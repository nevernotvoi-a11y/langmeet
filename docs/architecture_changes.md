# Изменения архитектуры LangMeet (итерация 2)

Изменения вносятся в архитектурные решения ЛР №3 и ЛР №4 и не меняют паттерн «Наблюдатель» через брокер сообщений.

## F1. Двухфакторная аутентификация

- Сервис аутентификации (домен «Пользователи и профили») получает проверку TOTP.
- Новая таблица `user_mfa` в базе домена «Пользователи и профили»: `user_id` (uuid, FK на users внутри домена), `totp_secret_encrypted` (bytea), `enabled` (boolean), `created_at`.
- Секрет TOTP хранится в зашифрованном виде; ключ шифрования — в переменных окружения, не в БД.
- Токен `mfa_token` имеет короткий срок жизни (5 минут) и используется только для запроса `/auth/2fa/verify`.
- Счётчик неверных кодов хранится в Redis (ключ по `user_id`), что соответствует принципу «при сбое — блокировать» (лекция 9).

## F2. Ускорение ответа API до p95 ≤ 200 мс

- Статусы заявок на подбор кэшируются в Redis (уже используется как очередь заявок Matching Service, ЛР №4, раздел 3.3).
- Для домена «Сессии и встречи» подключается read-реплика PostgreSQL: запросы `GET /sessions/{id}` идут на реплику, записи — на primary.
- API Gateway передаёт заголовок `Cache-Control: max-age=2` для ответов со статусом.
- Показатель p95 контролируется Prometheus и Grafana (ТЗ, раздел 4.3.5).
- Для перехода к реплике нужна согласованность «чтение после записи»: сразу после создания заявки статус берётся из Redis, а не из реплики.

## F3. Приглашение собеседника по ссылке

- Новая таблица `session_invitations` в базе домена «Сессии и встречи»: `id` (uuid), `session_id` (uuid, FK на sessions внутри домена), `created_by` (uuid, ссылка на users без FK, межсервисная), `token_hash`, `expires_at`, `status`.
- Приглашение не проходит через `match_requests` и очередь Matching Service.
- При принятии приглашения Сессии и встречи публикуют событие в брокер (`match.found` с признаком `source: invitation`), подписчики, как и раньше, создают сессию и отправляют уведомление (таблица 8 ЛР №4).

## F4. Экспорт отчёта сессии в PDF

- Формирование PDF выполняет сервис «Сессии и встречи» по данным `sessions` и `session_participants`.
- Отчёт не содержит данных, которых нет в домене сессий, поэтому межсервисные запросы не требуются.
- Файл не сохраняется в объектном хранилище, а формируется по запросу и отдаётся клиенту.

## Влияние на диаграмму компонентов (ЛР №3)

Изменений состава микросервисов нет. Добавляются связи: Redis ↔ Сессии и встречи (кэш статусов), PostgreSQL primary → read-реплика (домен Сессии и встречи).
